# Improve Skills

세션에서 쓴 스킬이 실제로 어떻게 굴러갔는지 보고, 고칠 점을 스킬 파일에 반영한다.
session-wrap에서 스킬 개선 부분만 떼어낸 것이며, 문서·자동화·후속작업 제안은 하지 않는다.
사람과 함께 쓴 스킬뿐 아니라 **훅이 무인으로 돌린 스킬 실행**(archive-me, improve-skills 자신 등)도 검토한다.

- 백업·변경 기록: `~/.claude/skills/.history/` (`CHANGELOG.md`, `PENDING.md`)
- 훅 실행 기록: `~/.claude/hooks/runs/<skill>/<id>/` (`input.*`, `stream.jsonl`, `meta.json`, 검토 후 `reviewed`)
- 훅: `~/.claude/hooks/session-close.sh` (clear·종료·compact 때 archive-me → improve-skills 순서로 실행)
- 스크립트: `~/.claude/skills/improve-skills/scripts/`

## 입력

| 인자 | 분석 대상 |
|------|-----------|
| 없음 | 현재 세션 |
| 스킬 이름 (예: `write-doc`) | 현재 세션 중 그 스킬 부분만 |
| `.jsonl` 경로 | 지난 세션. 먼저 `python3 ~/.claude/skills/improve-skills/scripts/extract_skill_session.py <경로>`로 요약본을 만들어 읽는다 |
| `runs` | 검토 대기 중인 훅 실행 기록. `reviewed` 파일이 없는 `~/.claude/hooks/runs/*/*/`마다 `digest_run.py <dir>`로 요약해 읽고, 검토가 끝나면 `reviewed`를 만든다 |
| `--hook <input.md>` | 훅 워커가 호출. 입력 파일에 원 세션 요약(A)과 훅 실행 요약(B)이 들어 있다. 아래 "hook 모드" 참고 |

대화형으로 실행할 때 `~/.claude/skills/.history/PENDING.md`에 항목이 있으면 같이 검토한다.
hook 모드가 사람 확인이 필요하다고 미뤄둔 수정안들이다. 반영했거나 기각한 항목은 지운다.

## Step 1: 사용된 스킬과 파일 위치 파악

- 현재 세션: `/스킬명` 호출과 Skill 도구 호출을 찾는다. 스킬 본문이 주입될 때 붙는 `Base directory for this skill: <경로>`가 스킬 위치다.
- 지난 세션: 추출 스크립트 출력의 `## 사용된 스킬`을 쓴다.
- `improve-skills` 자신도 대상이다.

각 스킬의 **수정 가능 여부**를 가른다:

| 위치 | 처리 |
|------|------|
| `~/.claude/skills/<name>/` (`synced/` 제외) | 직접 수정 |
| 프로젝트의 `.claude/skills/<name>/`, git 레포 아님 | 직접 수정 |
| 프로젝트의 `.claude/skills/<name>/`, git 레포 안 | 수정안(diff)만 제시. 사용자가 원하면 `~/.claude/skills/_shared/git-worktree.md` 절차로 반영 |
| 플러그인·번들·`synced/` 스킬 (위치 미확인 포함) | 수정 불가. 업데이트 때 덮어써진다. 필요한 보완은 관련된 사용자 스킬이나 auto memory에 두자고 제안만 한다 |

git 레포인지는 `git -C <스킬 디렉토리> rev-parse --show-toplevel`로 확인한다.

## Step 2: 개선 신호 수집

스킬을 쓰는 동안과 그 직후의 대화에서 아래 신호를 찾는다. 도구 출력의 세부보다 **사용자 발화**와 **스킬 지시와 실제 행동의 차이**가 핵심이다.

| 신호 | 예시 | 등급 |
|------|------|------|
| 사용자의 직접 지적·교정 | "그렇게 말고", "이건 빼", "매번 이거 물어보지 마", 결과물을 사용자가 고쳐서 다시 줌 | **A** |
| 스킬대로 했다가 실패하고 다른 방법으로 성공 | 스크립트 에러 후 우회, 권한 거부 후 다른 설정으로 해결, 경로·포맷이 바뀌어 있었음 | **A** |
| 스킬이 다루지 않는 상황을 즉석에서 처리했고 결과를 사용자가 받아들임 | 스킬에 없는 분기, 새 입력 형식 | **B** |
| 스킬 단계를 건너뛰었거나 사용자가 필요 없다고 함 | 확인 질문을 사용자가 매번 "그냥 해"로 넘김 | **B** |
| 대화에서 떠올린 개선 아이디어 (아직 검증 안 됨) | "이렇게 하면 더 나을 것 같은데" 수준 | **C** |
| 스킬 description이 트리거에 실패 | 써야 할 때 안 불렸거나, 엉뚱할 때 불림 | **A** (description 수정) |
| 훅 실행에서 권한 거부·도구 에러·비정상 종료 | digest의 `권한 거부`, `도구 에러`, `exit` | **A** |
| 훅 실행이 스스로 보고한 막힘 | digest의 `ISSUES(자기보고)` | **A** (지시가 모호했다는 보고면 B) |
| 훅 실행 결과가 스킬 규칙과 다름 | 도구 호출 순서·최종 응답을 SKILL.md 규칙과 대조해서 빠진 단계가 보임 | **B** |
| 훅이 만든 결과를 사용자가 나중에 대화에서 고침 | 아카이브 내용을 사용자가 정정함 | **A** |

훅 실행 기록을 볼 때는 digest만으로 판단이 안 되면 `stream.jsonl`과 `input.*`를 직접 읽는다.
문제 없는 실행도 같이 들어오는데, 이건 "규칙대로 했는지" 대조하는 용도다.

- **A, B는 반영한다.** B는 같은 방향의 근거가 세션에 있을 때만 반영한다.
- **C는 반영하지 않고** 보고에만 적는다. 나중에 실제로 겪으면 그때 A/B가 된다.

스킬이 아니라 다른 곳에 가야 할 신호는 여기서 처리하지 않고 보고에 한 줄로 남긴다:
- 여러 스킬에 공통인 작업 방식 선호 → auto memory `feedback` 또는 CLAUDE.md
- 사용자 개인에 대한 사실 → `archive-me`

## Step 3: 수정안 작성

각 신호마다 먼저 해당 스킬 파일 전체를 Read로 읽고, 다음 원칙으로 수정안을 만든다.

1. **고장 난 자리를 고친다.** 문제가 된 단계·문장을 찾아 그 자리를 바꾼다. 맨 끝에 "주의사항" 목록을 계속 덧붙이는 식으로 쌓지 않는다.
2. **사례가 아니라 규칙으로 쓴다.** 이번 세션의 특정 회사명·파일명을 박제하지 말고, 그 사례가 속한 일반 규칙과 이유를 쓴다. 사례는 괄호 속 예시로만 짧게.
   - 나쁨: "<COMPANY> 제출 문서는 1000자로 쓴다"
   - 좋음: "문항에 글자 수 제한이 있으면 공백 포함 기준으로 90~100% 범위를 맞춘다 (사용자가 여러 번 분량 부족을 지적함)"
3. **이유를 붙인다.** 규칙만 있으면 다음에 애매한 경우를 판단할 수 없다. 한 줄이면 된다.
4. **기존 내용과 충돌을 없앤다.** 새 규칙과 반대되는 기존 문장은 고치거나 지운다. 같은 말을 두 곳에 쓰지 않는다.
5. **스크립트 버그는 스크립트를 고친다.** 문서로 "이 스크립트는 X일 때 에러가 나니 Y 하라"고 우회시키지 않는다. 고친 뒤 실제로 한 번 실행해 확인한다.
6. **분량을 지킨다.** SKILL.md가 300줄을 넘어가면 세부 내용을 참조 파일(예: `reference.md`)로 빼고 SKILL.md에는 언제 읽을지만 남긴다.
7. **frontmatter를 보존한다.** `name`은 바꾸지 않는다. `description`은 트리거 문제가 있을 때만 바꾼다.

## Step 4: 적용

A/B 등급 수정안을 **사용자에게 미리 묻지 않고** 적용한다. 대신 되돌릴 수 있게 남긴다.

1. 백업: 수정할 스킬 디렉토리 전체를 복사한다.
   ```bash
   ts=$(date +%Y%m%d-%H%M%S)
   mkdir -p ~/.claude/skills/.history/<skill>/$ts
   cp -R <스킬 디렉토리>/. ~/.claude/skills/.history/<skill>/$ts/
   ```
2. Edit로 수정한다.
3. 변경 기록: `~/.claude/skills/.history/CHANGELOG.md` 맨 아래에 추가한다.
   ```
   ## YYYY-MM-DD <skill> (<ts>)
   - [A] <무엇을 바꿨나> — 근거: <세션에서 무슨 일이 있었나, 한 줄>
   - [B] ...
   ```
4. 사후 확인: 수정한 SKILL.md를 다시 처음부터 읽고 확인한다.
   - 단계 순서와 번호가 맞는가, 사용자 확인 지점이 의도치 않게 사라지지 않았나
   - 다른 단계와 모순되는 문장이 없나
   - 스크립트를 고쳤다면 실행해서 동작하는가

다음 경우에는 적용하지 않고 먼저 묻는다 (AskUserQuestion):
- 스킬의 목적이나 전체 흐름을 바꾸는 수정 (단계 삭제·재배치, 출력물 형식 변경)
- 사용자 확인 단계를 없애는 수정
- 근거가 사용자 지적 한 번뿐인데, 그 지적이 이번 경우에만 해당하는지 일반 규칙인지 애매할 때

## Step 5: 보고

```
스킬 개선 반영:
- write-doc/SKILL.md
  - [A] Step 3 분량 규칙 추가: 제한 글자 수의 90~100% — 근거: 분량 부족 지적 2회
  - [B] ...
- (수정 불가) update-config: <제안 내용>

반영 안 함 (C, 아이디어 단계):
- ...

다른 곳으로:
- memory feedback 후보: ...

되돌리기: cp -R ~/.claude/skills/.history/<skill>/<ts>/. <스킬 디렉토리>/
```

반영할 것이 없으면 "개선할 점 없음"과 그렇게 판단한 이유를 한두 줄로 말한다.

## hook 모드 (`--hook <input.md>`)

훅 워커가 사람 없이 띄운 세션이다. 파일 도구(Read/Write/Edit/Glob/Grep)만 있고 Bash는 없다.
워커가 이미 해둔 것: 입력 추출, 대상 스킬 스냅샷 백업, 실행 후 `reviewed` 표시와 처리 지점 기록.

1. `input.md`를 읽는다. A = 원 세션 요약, B = 훅 실행 요약들, C = 스킬 위치별 수정 가능 여부.
2. Step 1~3을 그대로 하되, Step 1의 수정 가능 여부는 **C를 그대로 따른다.** Bash가 없어서 git 여부를
   직접 확인할 수 없고, Glob으로 `.git`을 찾으면 홈 디렉토리 전체를 뒤지다 시간 초과가 난다.
3. 적용 범위가 대화형보다 좁다:
   - **A 등급만 직접 적용**한다. 문서(SKILL.md, 참조 md) 수정만 한다.
   - B 등급, 스크립트 수정(실행 검증을 못 하므로), Step 4의 "먼저 묻는" 경우는 적용하지 않고
     `~/.claude/skills/.history/PENDING.md`에 수정안(파일, 바꿀 위치, 바꿀 내용, 근거)을 적어둔다.
   - 백업은 워커가 했으니 Step 4의 백업 명령은 건너뛴다. `CHANGELOG.md` 기록은 한다 (`(hook)` 표시).
4. 보고는 최종 응답으로 대신한다. Step 5 형식으로 짧게.
