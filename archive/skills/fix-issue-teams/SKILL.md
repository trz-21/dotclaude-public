# Issue Fix Workflow (Agent Teams)

> **전제**: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 환경변수가 설정되어 있어야 한다.
> 실험적 기능이므로, 문제가 생기면 `/fix-issue`(subagent 버전)로 전환한다.

## 입력 정보

사용자로부터 아래 중 하나 이상을 받는다:
- **이슈 로그 content**: 에러/경고 로그 내용
- **Sentry 링크**: Sentry 이벤트 URL
- **자연어 문제 설명**: 유저가 경험하는 증상 설명
- **Project source**: 어떤 프로젝트에서 발생했는지

## 대상 레포지토리

> **Reference**: `~/.claude/skills/_shared/repos.md`

## 팀 구성

### 팀 리드 (메인 세션)

> 너는 이슈 수정 프로젝트의 **팀 리드**다.
> 전체 워크플로우를 조율하고, 팀원들의 결과를 종합하여 판단한다.
> 직접 코드를 탐색하거나 수정하지 않는다. 팀원에게 위임하고 결과를 검토한다.
> 사용자와의 커뮤니케이션은 팀 리드만 담당한다.

### 팀원 페르소나

팀원을 생성할 때 아래 페르소나를 부여한다.
레포별 전문가 페르소나는 공유 파일의 내용을 읽어서 주입한다.

- **팀원 A — <SERVER_REPO> 전문가**: `~/.claude/skills/_shared/personas/repo-expert-server.md`
- **팀원 B — <APP_REPO> 전문가**: `~/.claude/skills/_shared/personas/repo-expert-app.md`
- **팀원 C — <VOICE_AGENT_REPO> 전문가**: `~/.claude/skills/_shared/personas/repo-expert-voice-agent.md`

**팀원 D — 검증 전문가 (Phase 5에서 합류):**
> 너는 소프트웨어 QA, 비용 분석, DB 동시성, 성능 분석 전문가다.
> 코드 변경이 기존 기능을 깨뜨리지 않는지, 외부 API 비용이 증가하지 않는지, DB 트랜잭션/락 문제가 없는지, 유저 레이턴시에 영향이 없는지 종합 검증한다.
> uvicorn 7 workers 환경의 동시성, Tortoise ORM + aiomysql 커넥션 풀(min=2, max=10), voice-agent 음성 파이프라인 지연을 이해한다.
> 낙관적 판단을 하지 않는다. 문제가 될 수 있는 경우를 적극적으로 찾는다.

## 워크플로우

### Phase 1: 팀 리드 — 입력 분석 및 팀원 배치

1. 입력 유형을 판별한다 (Sentry / 자연어 / 혼합).
2. 팀원 A, B, C를 생성하고, 각각에게 **자신의 레포에서 이슈 관련 코드를 탐색**하도록 지시한다.
   - Sentry 입력: 에러 메시지, 스택트레이스, 함수명 등 검색 키워드를 전달
   - 자연어 입력: 문제 설명에서 추출한 기능 키워드를 전달
3. 팀원들이 동시에 탐색을 시작한다.

### Phase 2: 팀원 A/B/C — 병렬 코드 탐색

각 팀원은 자신의 담당 레포에서:
1. 키워드로 관련 코드를 검색한다.
2. 매칭되는 코드의 호출 체인, 조건문, 에러 핸들링을 분석한다.
3. 해당 레포에서 발생 가능한 시나리오를 나열한다.
4. 다른 레포와의 연동 지점(API 호출, 이벤트, WebSocket)을 식별한다.
5. **결과를 팀 리드에게 보고한다.**

팀원 간 크로스 레포 확인이 필요한 경우:
- 팀원 A가 API 엔드포인트를 발견하면 → 팀원 B에게 "이 API를 호출하는 클라이언트 코드 확인해줘"라고 직접 메시지
- 팀원 C가 서버 API 의존성을 발견하면 → 팀원 A에게 "이 엔드포인트의 응답 형식 확인해줘"라고 직접 메시지

### Phase 3: 팀 리드 — 종합 분석 및 수정 계획

1. 팀원들의 보고를 종합한다.
2. 시나리오를 분류한다 (Sentry: A/B/C 분류, 자연어: 유력 원인 판단).
3. 진행 불가 판단:
   - 코드 레벨에서 해결 불가 → 사용자에게 보고
   - 코드에서 확인 불가능한 맥락 필요 → 사용자에게 질문 (코드에서 알 수 있는 건 물어보지 않음)
4. 공식 문서를 참조하여 수정 계획을 수립한다.
5. 수정이 필요한 레포의 팀원에게 **구현 태스크를 할당**한다.

Sentry 입력인 경우, 이 시점에서 사용자에게 시나리오 분석 결과를 보고한다.

### Phase 4: 팀원 — 병렬 구현

#### 4-0. Worktree 생성 (팀 리드가 수행)

`~/.claude/skills/_shared/git-worktree.md`의 **Worktree 생성** 절차를 따른다.
prefix는 `fix`를 사용하여, 수정 대상 레포에만 worktree를 생성한다.

각 팀원에게 worktree 경로 (`${WORKTREE_BASE}/<REPO>`)를 전달한다.

#### 구현

팀 리드가 할당한 태스크에 따라 각 팀원이 **worktree 경로에서** 자신의 레포를 수정한다.

각 팀원은:
1. **Worktree 경로에서 작업한다**: `${WORKTREE_BASE}/<REPO>` 경로의 파일을 수정한다. 원본 레포 경로를 수정하지 않는다.
2. 수정에 사용하는 API/패턴의 **공식 문서를 확인**한다.
3. 수정 코드를 작성한다.
4. 코드 레벨에서 재확인한다.
5. 이슈와 무관한 코드를 변경하지 않는다.
6. **완료를 팀 리드에게 보고한다.**

레포 간 의존성이 있는 경우:
- 팀 리드가 Task List에 `blockedBy`로 의존성을 설정한다.
- 선행 팀원이 완료 보고 후, 후행 팀원이 작업을 시작한다.
- 선행 팀원이 후행 팀원에게 직접 "API 응답 형식을 이렇게 바꿨으니 참고해"라고 메시지할 수 있다.

### Phase 5: 팀원 D 합류 — 검증

1. 팀 리드가 팀원 D(검증 전문가)를 생성한다.
2. 팀원 D에게 **모든 레포의 변경 diff**와 **worktree 경로**를 전달한다. 검증 시 코드를 읽을 때는 worktree 경로에서 읽는다.
3. 팀원 D는 아래를 종합 검증한다:
   - 문제 해결 완전성 + regression + 사이드이펙트
   - 외부 서비스 비용 영향
   - DB 트랜잭션/Lock + uvicorn 멀티워커 동시성
   - 유저 경험 레이턴시
4. 필요시 팀원 A/B/C에게 직접 질문한다 ("이 변경이 fallback 체인에 영향 주지 않는지 확인해줘").
5. **검증 결과를 팀 리드에게 보고한다.**

### Phase 5 결과 처리

팀 리드가 팀원 D의 검증 결과를 종합하여 **사용자에게 보고하고 확인받는다.**
문제가 발견되면 **Phase 3으로 돌아가** 계획을 재수립한 뒤 Phase 4 → Phase 5를 다시 수행한다.

### Phase 6: 팀 리드 — 커밋 및 Worktree 정리

`~/.claude/skills/_shared/git-worktree.md`의 **커밋**, **후속 옵션**, **정리** 절차를 따른다.

1. 각 worktree에서 변경사항을 리뷰하고 커밋한다.
2. 사용자에게 머지 / PR / 보류 옵션을 안내한다.
3. 사용자 승인 후 worktree와 브랜치를 정리한다.

## Teams vs Subagent 차이점

| | subagent (`/fix-issue`) | teams (`/fix-issue-teams`) |
|---|---|---|
| **커뮤니케이션** | 메인 → subagent → 메인 (hub-spoke) | 팀원 간 직접 메시지 가능 (mesh) |
| **크로스 레포 확인** | 메인이 중계 | 팀원 A ↔ 팀원 B 직접 대화 |
| **검증** | 4개 독립 subagent | 검증 팀원이 구현 팀원에게 직접 질문 |
| **컨텍스트** | subagent마다 독립 | 팀원이 세션 내내 컨텍스트 유지 |
| **토큰 비용** | 필요한 Phase에서만 소비 | 팀원이 대기 중에도 소비 |

## 규칙

- 팀 리드만 사용자와 소통한다. 팀원이 직접 사용자에게 보고하지 않는다.
- Sentry 입력: Phase 3에서 시나리오 분석 보고, Phase 5에서 검증 결과 보고.
- 자연어 입력: Phase 5에서 검증 결과 보고만.
- Phase 3에서 진행 불가하거나 코드에서 확인 불가능한 맥락이 필요하면 사용자에게 보고.
- 팀원 간 직접 메시지는 **크로스 레포 확인이 필요할 때만** 사용한다.
- 확신이 없으면 멈추고 질문한다. 추측하지 않는다.
- 이슈와 무관한 코드를 변경하지 않는다.
